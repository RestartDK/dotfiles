### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.** For "land the stack", "ship it", "enable merge when ready", or an explicitly authorized landing of a stack that **Babysit** already drove to green.

This is the authorized landing phase alongside `~/.agents/skills/dstack/dstack-mode/playbooks/babysit.md`. Babysit makes a PR or stack mergeable and keeps watching through merge and cleanup. Shipping decides what is actually safe to merge. On GitHub, use native stacks through the official `github/gh-stack` extension. Read `~/.agents/skills/dstack/dstack-mode/references/github-stacks.md` before merging. Green is not safe, and the gap between those two words is where this playbook lives.

1. **Verify every PR independently before arming anything.** One subagent per PR, not batched, each an independent subagent, each exercising the real surface (headless chromium or browser automation for UIs, the CLI itself for CLIs) against parent versus head. Each verifier also applies the **thermo-nuclear-code-quality-review** standard to the diff, and its presumptive blockers fail the verdict the same as behavioral breakage. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR so the record outlives the chat. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that the verdicts still describe the code.** A restack rewrites every SHA above it and silently invalidates every verdict without touching a single check. Compare `git patch-id` at the verdict SHA against the current head before trusting an older verdict, and re-verify anything that actually drifted. Twenty-one verdicts went stale this way in one run with no signal at all.
4. **Merge through the verified ceiling.** Capture the stack order and current head SHAs with `gh stack view --json` and `gh pr view`. For a native stack, run `gh stack merge <ceiling-pr-number> --yes --squash` if squash is the repository's chosen method. Otherwise select its permitted `--merge` or `--rebase` method. Confirm the number identifies the ceiling PR, not the stack. Never omit the argument or pass a stack number unless the entire stack is verified. GitHub merges the selected prefix atomically when no merge queue applies. With a merge queue, it enqueues the selected PRs together, but they may land in separate groups and the queue chooses the method. For a standalone PR, use `gh pr merge` with the repository's chosen method. Use `--auto` only when waiting is required. If native stacks are unavailable, merge only a verified root targeting trunk, then rebase and re-verify the next approved slice before proceeding.
5. **Never enable per-PR auto-merge on a dependent child.** Only the root targets protected trunk. A child may target an unprotected parent and read `CLEAN`, so `gh pr merge` can merge it into that parent. Use the native stack merge from step 4 instead. If a previous agent armed child auto-merge, disarm with `gh pr merge <n> --disable-auto` and confirm the field is back off.
6. **Confirm the result on GitHub.** Check the selected PRs' merged or queued state with `gh stack view` and GitHub's merge queue. An `autoMergeRequest` field alone does not prove that a native stack is queued. If confirmation is unavailable, say so rather than infer it.
7. **Once a queue is draining, stop touching its branches.** No restacks, speculative pushes, or commands that rewrite or retarget queued work. This includes `gh stack sync`, `rebase`, `push`, `submit`, `modify`, `link`, and `unstack`. Independent work starts from trunk and ships on its own.
8. **Watch the drain, do not drive it.** Keep the frozen bottom-to-top PR list through the ceiling. Use GitHub's queue state and `watch-pr <pr-number> --status-only` for each selected PR. The watcher reports one PR at a time and its merged verdict is `MERGED`. A `READY` verdict is not proof of a merge. Run checks in a work pane through herdr `run` with `wait: true` or `notify: true`. Report each merge, but stop only when every selected PR is `MERGED`. Do not rediscover the list after a partial merge, because GitHub may retarget the remaining stack. If the queue stalls, diagnose before mutating.
9. **Clean up and stop at the ceiling.** When the verified run is merged, complete Babysit's resource cleanup for those PRs before declaring done. Preserve anything still owned by unmerged work. Report what landed, which resources were stopped or deliberately retained, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
