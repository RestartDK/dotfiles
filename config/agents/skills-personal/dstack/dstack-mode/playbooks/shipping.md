### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.** For "land the stack", "ship it", "enable merge when ready", or the second half of a stack that **Babysit** already drove to green.

This is the half after `~/.agents/skills/dstack/dstack-mode/playbooks/babysit.md`. Babysit makes a PR or stack mergeable. Shipping decides what is actually safe to merge and lands it through the available hosting path. Green is not safe, and the gap between those two words is where this playbook lives.

1. **Verify every PR independently before arming anything.** One subagent per PR, not batched, each an independent subagent, each exercising the real surface (headless chromium or browser automation for UIs, the CLI itself for CLIs) against parent versus head. Each verifier also applies the **thermo-nuclear-code-quality-review** standard to the diff, and its presumptive blockers fail the verdict the same as behavioral breakage. Each returns `PASS`, `PASS+NOTES` or `FAIL` and posts that verdict on its own PR so the record outlives the chat. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that the verdicts still describe the code.** A restack rewrites every SHA above it and silently invalidates every verdict without touching a single check. Compare `git patch-id` at the verdict SHA against the current head before trusting an older verdict, and re-verify anything that actually drifted. Twenty-one verdicts went stale this way in one run with no signal at all.
4. **Use the merge path that is actually available.** Graphite is optional. Use it only when `gt` is available and authenticated, the repository is synced, and the branches are tracked. In that case, arm merge-when-ready and pass `--always`; a no-op submit skips the Graphite update and silently arms nothing.
   ```bash
   gt submit --merge-when-ready --always --update-only --no-interactive
   ```
   Otherwise use the hosting provider directly. On GitHub, merge a verified single PR with the repository's chosen method through `gh pr merge`; use `--auto` only when branch protection or the merge queue requires waiting. For dependent changes without Graphite, merge the root, rebase the next change onto trunk, re-verify it, and continue one PR at a time.
5. **Never enable GitHub auto-merge on a dependent stack.** Only the root targets protected trunk. Every child targets its unprotected parent branch and can already read `CLEAN`, so GitHub may merge children into parents immediately and collapse the stack into itself. If a previous agent armed it, disarm with `gh pr merge <n> --disable-auto` and confirm the field is back off.
6. **Confirm arming through the tool that owns the queue.** For Graphite, do not read `autoMergeRequest` as proof that MWR is armed; it stays off until Graphite reaches that PR at the queue front. Confirm arming from Graphite's own state. For a hosting-provider queue, confirm through that provider. If confirmation is unavailable, say so rather than infer it.
7. **Once a queue is draining, stop touching its branches.** No restacks, speculative pushes, or submit commands that can rewrite or retarget queued work. With Graphite, this also means no `gt sync` or `gt submit --stack`; even plain `gt submit` is unsafe until local parentage is checked. Independent work gets re-parented onto trunk and shipped on its own.
8. **Watch the drain, do not drive it.** Arm the watcher in queued mode over the verified run with the herdr tool's `run` and `notify: true`, re-armed after any verdict you act on, until COMPLETE at the ceiling. ADVANCE is progress, not termination. Under Graphite, bases retarget and `graphite-base/*` refs get cut as each PR merges; that is expected. Under a direct hosting-provider path, watch each PR to completion before preparing the next dependent change. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating, because a stalled queue and a broken stack look identical from the outside.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
